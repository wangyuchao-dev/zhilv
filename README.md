# 知旅 · 智能旅行规划系统

RAG Agent 驱动的行程规划：**结构化输入 → 需求解析 → 攻略检索 → 行程编排 → 结构化输出 → 保存到库 → 历史回看**。

---

```bash
conda activate zhilv
cd backend
uvicorn app.main:app --reload --port 8000
```

- 健康检查：<http://127.0.0.1:8000/api/health>

```bash
cd frontend

```

- 页面：<http://127.0.0.1:5173>

### 依赖服务

| 服务 | 地址 | 说明 |
|---|---|---|
| PostgreSQL | `127.0.0.1:5432` | 库 `zhilv`，账号 `postgres`（口令见 `.env`）（Docker 容器 `pgvector-pg17`） |
| Redis | `127.0.0.1:6379` | 无密码 |
| Chroma | `backend/db/chroma_db` | 本地文件，7 个城市攻略已入库 |

> 想用 SQLite 就把 `DATABASE_URL` 改成 `sqlite:///./db/zhilv.db`，模型代码不用动。

## 二、整体链路

```
Vue 规划页（12 个字段的表单）
    │  POST /api/plans/generate
    ▼
FastAPI Router  ── 立刻返回 202 + task_id（0.05 秒，不等生成）
    │                命中缓存时直接带结果返回，前端不用轮询
    ▼
后台线程池（ThreadPoolExecutor，2 并发）
    │
    ├─ Agent 1「需求解析」  表单 → 3 条检索查询 + 重点 + 避坑
    │         ↓ 进度 1/4  写入 Redis
    ├─ RAG 检索            按城市过滤，多 query 合并去重，取 top-(天数×2)
    │         ↓ 进度 2/4
    └─ Agent 2「行程编排」  需求 + 素材 → 结构化 JSON（Pydantic 强约束）
              ↓ 进度 3/4 → 完成 4/4
    │
    ▼
Vue 每 800ms 轮询 GET /api/plans/task/{id}
    │  状态栏显示：正在解析需求 → 正在检索攻略 → 正在编排行程
    ▼
拿到结果 → 结果页（卡片式展示 + 右上角保存）
    │  POST /api/plans（带 task_id）
    ▼
PostgreSQL  ── 历史页读取
```

### 为什么拆两个 Agent

- **Agent 1** 只干一件事：把用户填的表翻译成检索指令。
  直接把整段表单丢给向量库效果很差 —— 向量模型对长句不敏感，而且「亲子」这种偏好需要转成具体检索意图。
- **Agent 2** 只干一件事：拿素材排行程。
  Prompt 里强制「景点必须来自资料，不许编」，避免模型瞎编店名和价格。

拆开之后，两段的 prompt 都更短、约束更明确，出问题也好定位。

## 三、Redis 用在哪

| 用途 | Key | TTL | 解决什么 |
|---|---|---|---|
| **结果缓存** | `plan:cache:{表单hash}` | 30 分钟 | 同样输入不重复调模型。实测 **14.1s → 0.03s** |
| **任务状态** | `plan:task:{task_id}` | 1 小时 | 记录「解析需求 1/4 → 检索攻略 2/4 → 编排行程 3/4 → 完成 4/4」，前端每 800ms 轮询显示进度条 |
| **接口限流** | `rate:{ip}` | 60 秒 | 每 IP 每分钟最多 20 次，防连点烧 token |
| **生成结果** | `plan:result:{task_id}` | 1 小时 | 轮询到 done 时直接取，省得前端再发一次请求 |
| **天气缓存** | `weather:{城市}:{起}:{止}` | 3 小时 | 天气只由城市+日期决定，与表单其它字段无关，命中率最高。省 2.9s/次 |
| **检索结果** | `retr:{城市}:{top_k}:{阈值}:{语料指纹}:{queries}` | 30 分钟 | 一次命中免掉 embedding + Chroma + 阈值过滤。实测 **4.18s → 0.32s** |


> **不是每环都加。** 判断标准是「净收益 =（原耗时 − 缓存后耗时）× 命中率 − 维护成本」：
> Chroma 查询 50ms、阈值过滤微秒级，加 Redis 反而更慢；Agent1 缓存与结果缓存同维度，属于重复建设。
> 检索缓存的 key 带「语料指纹」（7 个 md 的 mtime + size 哈希），改任何一份攻略缓存自动失效，不用手动清 Redis。
> 空结果不缓存 —— 一次 embedding 抖动不能污染接下来 30 分钟。

## 六、检索阈值是怎么定出来的

不是拍脑袋设的，是**实测分数分布**倒推的（text-embedding-v4 + 当前 7 城语料，
21 次真实检索 / 105 个片段）：

| 问题类型 | top1 分数范围 | 例子 |
|---|---|---|
| 语料里明确有 | 0.892 – 0.920 | `大连 星海广场 门票` |
| **Agent 真实产出的查询** | **0.807 – 0.858** | `大连 自然风景 景点推荐` |
| 语料里根本没有 | 0.730 – 0.786 | `大连 潜水 深潜 考证` |

**0.80 卡在「无关最高 0.7863」和「有用最低 0.8070」之间**——
挡住 7/7 个无关问题，同时保住真实查询。0.75 会让 5/7 个无关问题通过（等于没设），
0.82 开始误杀最弱的真实查询。

> 早先定过 0.75，错在拿**人工精修的问题**去测；真实系统跑的是 Agent 1 生成的关键词式短句，
> 分数更低。**定阈值必须用线上真实查询，不能用开卷考。**

### 降级重查

固定阈值天生会漂（换模型、加语料、加城市）。所以：

```
正常检索 MIN_SCORE=0.80
   ↓ 合并后不足 2 条
放宽到 0.79 再查一次，且只保留 top-1（不放大 top_k）
   ↓ 写 WARNING 日志，带「今日第 N 次降级」
```

> 为什么是 0.79 而不是 0.75：实测无关问题 top1 落在 0.730–0.786，
> 0.75 会把 7 个里的 5 个整批放回，等于把 0.80 刚挡住的洞又打开。
> 0.79 仍卡在「无关最高 0.7863」和「有用最低 0.807」之间。
> 降级只留 top-1 —— 宁可少给素材，不硬塞一堆不相关内容。

**降级次数是重调阈值的信号**：如果频繁触发，说明系统其实一直在用 0.75 跑，
这时就该重测分数分布，而不是让 README 里的 0.80 变成一个假数字。

注意：行程规划场景下用户提交的是表单，目的地一定在语料内，
所以检索为空是**异常**（阈值误杀 / embedding 故障），不是「用户问了没答案」。

### 编排能力是真的吗（语料为什么不给现成行程）

早期每城语料里都写了一份「经典三日行程参考」。实测 **7/7 城市检索 top-1 都命中它** ——
检索把现成行程捞出来，模型只需复述成 JSON，看起来编排很强，实际没验证过。

所以把整章改写成 **「片区组合与交通衔接」**：

```
原来（给答案）：第一天 上午星海广场 / 下午滨海步道 / 晚上星海小吃街
现在（给素材）：星海广场片区：星海广场、滨海步道、小吃街；
                建议半天；地铁 2 号线；适合傍晚看日落
```

保留景点名、地理组合、时长、到达方式，**去掉「第几天 / 上午下午」的顺序决策**。
模型仍要自己决定哪天去哪个片区、按人数和节奏分配时段、算预算。

改写后实测 top-1：成都=目的地简介、大连=金石滩片区、西安=回民街 —— 不再是预写行程。

> 答辩可以这样验证编排能力：同一城市、同一日期，只改偏好（如「亲子」vs「美食历史」）
> 各生成一次，对比两份行程的顺序与景点是否不同。

## 七、几个实现细节

**表单校验双保险**
前端失焦即时提示，后端 Pydantic 再校验一遍（`ge`/`le`/`Literal`/`field_validator`）。
天数根据起止日期自动算，如果前端传错，后端以日期为准自动纠正。

**结构化输出的稳定性**
用 `with_structured_output(TravelPlanBody)`，让模型按 Pydantic schema 填，
而不是自由输出再解析 JSON。字段缺失、层级错乱、类型不对的情况基本消失。

**检索按城市过滤**
7 个城市各一个 md 文件，检索时用 metadata 过滤 `source == dalian_guide.md`，
否则问大连会混进成都的攻略。

**切分噪声**
按 `##` / `###` 标题切，会切出只有一行标题的碎块（比如 `# 2026大连深度游玩全攻略`），
这种块向量上很容易命中但没有价值，检索时按长度 < 40 字丢掉。

## 九、已知边界

- **服务韧性**：Agent 懒加载（没配 Key 也能起服务、`/health` 会报 `llm_configured=false`）、
  模型调用 60 秒超时、在途任务上限 2 个（超了返回 503）、同表单并发只跑一次
- **阈值会过期**：`MIN_SCORE=0.80` 只适用于当前 embedding 模型 + 7 城语料；换模型或加城市必须重测。
  降级日志里的次数就是重测信号
- **没有 rerank**：阈值只能判「相不相关」，判不了「对不对题」。
  当前按城市过滤后候选只有 11–17 个 chunk，加交叉编码收益有限；候选量上来后应接 rerank
- **支持 2–5 天**：每城 11–12 个景点，每天用 2 个（上午+下午），5 天刚好用满；超过 5 天必然重复，所以上限卡在 5
- 想扩城市：往 `data/` 放 `<city>_guide.md`（格式照现有文件），再跑 `python scripts/ingest_data.py`
- 想扩天数：每城补到 15 个景点以上，再把 `schemas/plan.py` 的 `le=5` 调大
- 生成一次 12–15 秒（qwen-flash），缓存后 0.03 秒
- 任务是同步生成的，量大时应该改成后台队列（Redis 里已经有 task 状态，接 Celery/RQ 很顺）
- 前端没做登录，历史是所有人共用的
